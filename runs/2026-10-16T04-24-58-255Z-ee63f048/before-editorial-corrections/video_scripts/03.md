**NARRATION:**
Start with what "using an agent" actually requires from the developer.

GitHub's skills guidance describes the work as an active coordination role—not passive automation. The job is: define the problem clearly, evaluate what the agent produces, and make sound technical decisions about what's ready to ship. [03-c1]

That framing is optimistic. But notice its implicit assumption: you already have enough domain knowledge to judge whether the agent got it right. If you don't yet know what "right" looks like in a given area, the guidance doesn't tell you how to build that judgment.

**[ON-SCREEN SOURCE CUE: Stack Overflow Blog, "Production-grade LLMs and agents: a field guide," Oct 8 2026]**

**NARRATION:**
Stack Overflow published a production maturity model for agent systems—six levels, each one assuming the previous is already in place. [03-c3]

Level zero is a notebook demo. Level one requires agents to *propose* changes rather than apply them directly. Level two requires evaluation pipelines gated into your CI process. Level four requires layered guardrails, a redacted audit log, and memory scoped per tenant. Level five requires a dashboard showing every decision the agent made, what it cost, and a kill switch that works in seconds without a deploy.

The model includes a ten-item self-assessment. Its verdict for teams that tick fewer than half: *you are earlier than the demo suggests.*

This is a practical guide, not an independent audit of real teams. But its checklist is concrete—and most items on it require non-trivial infrastructure investment.

**NARRATION:**
Now add security.

GitHub reports that push protection currently stops roughly 30 percent of newly detected secrets before they enter repository history. The remaining 70 percent are found after the credential is already exposed—and cleaning those up requires developer time, not just compute. [03-c4]

A new AI classifier, currently in private preview, could more than double prevention coverage. It will consume AI credits when it ships.

The structural point here is important for small teams: an agent writing more code generates more potential exposures. Prevention scales with spending. Remediation scales with people. If your team is one or two people, that second scaling curve is a real problem.

GitHub has a commercial interest in you adopting its security products. Treat these figures as source claims—but the logic of the scaling gap holds regardless of who is reporting it.

**[VISUAL: Simple text summary card — three bullet points]**

**NARRATION:**
Put these sources together and an inference emerges—one worth stating carefully. [03-c6]

The practical baseline for responsible agent adoption involves: domain expertise sufficient to evaluate what the agent produces, permission architecture that requires admin-level setup, evaluation infrastructure built into your CI process, and paid security tooling. That baseline is higher than any single source acknowledges on its own—and the costs fall unevenly on teams without a dedicated infrastructure budget.

But this remains an inference from converging signals. None of these sources studied teams that tried adoption and found it unworkable. None address accessibility constraints or specific cost thresholds for students. The security incidents discussed in the podcast involve unreleased models in controlled training environments—not a student running a coding agent on a side project locally. An alternative reading of the same evidence is that incremental adoption—starting at the lower rungs of the maturity model and building upward—is viable. The question the evidence doesn't answer is whether that ladder is climbable without a budget.

**NARRATION:**
So here is the question worth sitting with before you commit to any of this.

If responsible adoption requires administrative access, CI infrastructure, paid tooling, and enough domain expertise to judge agent output—who, specifically, is the "start today" pitch aimed at?

The sources describe developers doing two jobs at once: the work itself, and the work of staying current with tools that change faster than most teams can absorb. That dual burden falls hardest on people with the least infrastructure to absorb it.

The useful question isn't "can we use this tool?" It's: which level of the maturity model are we actually at—and what would it concretely cost to move one level higher?
