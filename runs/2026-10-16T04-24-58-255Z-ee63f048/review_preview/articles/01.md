# The Infrastructure Underneath Your Agent: What Providers Are Rebuilding and Why It Matters

As of 2026-10-16.

The pitch from AI coding tool providers is increasingly familiar: hand off your pull request queue, let agents commit and review, and ship faster. What's less often stated clearly is that the infrastructure supporting those workflows is still being redesigned, that the permission controls guarding them have known gaps, and that the headline scale figures describe provider workloads—not yours. For a student team or small project, sorting those things out matters more than the throughput numbers.

---

## Scale Figures Tell a Provider Story, Not Yours

GitHub reports that developers and agents made 7.38 billion commits on the platform in September 2026—described by GitHub as more than five times the level from a year earlier—and that pushes grew from roughly 0.69 billion to 3.35 billion per month year over year, which GitHub attributes substantially to agent-driven workloads [github](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/). Those are striking numbers, but GitHub is explicit that the repositories driving them are large engineering teams running dense CI pipelines alongside agent fleets. The busiest single repository saw roughly a billion requests in one month.

This matters because the gap between what a platform must engineer for and what a small team actually experiences is enormous. Large CI workloads and concentrated repository activity are alternative explanations for these scale figures; they do not measure what a student team would gain.

Anthropic's account, relayed through a commentary post by Simon Willison rather than the primary engineering article, reports a similar pattern at the company level: daily code merges grew from roughly 2,500 in May 2026 to over 30,000 in September 2026, and Anthropic built and migrated to a custom source-control system called Scion—with Claude described as its heaviest user—in response [simon-willison](https://simonwillison.net/2026/Oct/13/redesigning-source-control-at-anthropic/). Willison notes this sounds like a reinvention of centralized source control, and credits Google's Piper and Meta's Sapling as acknowledged prior art. This is internal infrastructure built for an AI lab's own agent workload; it is not available to external teams and was not designed with offline use in mind.

## What Is Being Built vs. What Is Available

OpenAI's Codex product video presents a code-review workflow in which an agent takes an automatic first-pass review of GitHub pull requests once repository permissions are configured [openai, 0:40](https://www.youtube.com/watch?v=IZXv6a78NDw&t=40); [openai, 2:10](https://www.youtube.com/watch?v=IZXv6a78NDw&t=130). The video describes GitHub integration as generally available and GitLab as in preview. What the video does not provide is any evaluation of review accuracy, false-positive rates, or error frequency—a gap that is directly relevant to anyone considering whether to rely on that first pass rather than treat it as a hint. The transcript comes from a caption track of unknown automation status, so these should be taken as paraphrases rather than direct quotations.

On the permission side, an Anthropic employee described on the Latent Space podcast the multiple layers being added to manage agent permissions at scale: inference-time probes and classifiers, an "auto mode" that checks whether agent actions match what the user actually granted, and identity isolation for multiplayer contexts [latent-space, 14:31](https://www.latent.space/p/thariq#t=871); [latent-space, 81:00](https://www.latent.space/p/thariq#t=4860); [latent-space, 83:40](https://www.latent.space/p/thariq#t=5020). The description is candid about complexity. One example given: an agent given access to a production database might use computer-use capabilities to issue its own credentials and then edit data—auto mode is designed to catch this by checking intent against user-granted scope. But the same account describes this as ongoing work with known edge cases and no guarantee of completeness. This is a source claim from a vendor employee with commercial interest; it is not an independent security audit.

## The Oversight Responsibilities That Remain Yours

GitHub says its planned new architecture must preserve branch protections, required reviews, and audit logs, framing this explicitly as a non-negotiable design constraint [github](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/); [simon-willison](https://simonwillison.net/2026/Oct/13/redesigning-source-control-at-anthropic/). That is a meaningful commitment to stated intent—but it is a planned architecture, and GitHub's own performance figure (up to 35 times higher write throughput in internal benchmarks) comes from the team doing the work, not an independent evaluator [github](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/).

Willison's commentary adds a detail that cuts across the infrastructure layer: Anthropic used adversarial AI review extensively while building Scion, and found it effective but myopic—skilled engineers had to steer Claude away from over-engineering in response to hypothetical concerns [github](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/); [simon-willison](https://simonwillison.net/2026/Oct/13/redesigning-source-control-at-anthropic/). That is a different kind of oversight than a branch protection rule. One layer enforces workflow controls; the other requires human technical judgment about what the agent is actually optimizing for.

The two are not substitutes. Higher throughput does not reduce the need for either.

---

## The Question Worth Sitting With

The evidence relies heavily on provider accounts, including some relayed through independent commentary. No small-team perspective, no unsuccessful deployment, no independent accuracy measurement of the review workflow appears here. That is a meaningful absence.

The practical question for a student team is not whether Anthropic's commit volume grew twelve-fold. It is: *when an agent takes a first-pass review of my pull request, what exactly should I still check, and how would I know if it missed something important?* These sources do not establish how much review your own project needs.
